## Problem

**The site validates a person graph and then flattens it to text.**
`projects.team`, `events.hosts`, `learn.authors`, `posts.author` and
`programs.lead` are all `reference('people')`, checked at build time and
resolved through `resolveReferences()` in `src/lib/content.ts`. Then every page
that consumes one does the same thing with the result:

```ts
team.length ? ['Team', team.map((person) => person.data.name).join(', ')] : null
```

— `src/pages/projects/[slug].astro`, and the same shape in `events/[slug].astro`
(`hosts`) and `learn/[slug].astro` (`authors`). A comma-separated string in a
spec table. **No person's name is a link anywhere on qairuhub.com.** The only
link to a person at all is in `PeopleStrip.astro`, which points at
`/people#<id>` — and the strip's main use is on `/people`, so that is a link to
the page you are standing on. There is no `src/pages/people/[slug].astro`.

So the graph is traversed in neither direction. Every fact a member page would
need — who built what, who ran which session, with dates and repo links already
attached — exists and is already type-checked. It is used to print names.

The cost lands on students. Eight weeks of evenings on a builder community is
defensible mainly because afterwards you can point an internship reviewer at
something. Today the strongest artefact QairuHub can hand a member is a Telegram
handle: "Member, QairuHub" is an unverifiable claim, and a URL naming what you
built, when, with the repo attached, is not.

The second half is worse, because it is about other people's data.
`docs/CONTENT.md` states the rule — *"Nobody is listed without agreeing to
be"* — as prose in a document. Nothing in `src/content.config.ts` can tell a
consented entry from an unconsented one, and nothing records who asked, when, or
what was agreed to. (`active` is not the gap: it carries a doc comment and
proposal 003 defines its transitions. This proposal must not answer that
question a second time.)

**What the law actually says, stated precisely because the compliance version of
this argument is the tempting one.** Kazakhstan's Law No. 94-V of 21 May 2013 on
Personal Data and its Protection requires consent — in writing or another form
that confirms receipt — before personal data is collected and processed, lets the
subject revoke that consent, and gives the owner fifteen business days to stop or
issue a reasoned refusal
([DLA Piper, *Data Protection Laws of the World* — Kazakhstan](https://www.dlapiperdataprotection.com/index.html?t=law&c=KZ)).
It does **not** require consent to carry an expiry date. The annual review below
is our own rule, chosen because a first-year's willingness to be photographed on
a public site is not a fact that stays true for four years. Do not sell it as
compliance.

## Prior art

**[Recurse Center — the User's Manual](https://www.recurse.com/manual).** The
directory is a findability device, not a scoreboard: you add a photo and bio
because *"knowing each other is an important foundation for the culture we want
to cultivate,"* on a site whose first principle is *"We don't have grades, exams,
curricula, or even classes."* No score, no rank, no completion. Leaving does not
end the relationship — *"Alums are welcome to program, chat, host and attend
events at RC all day, every day, regardless of when you attended RC."*
**Steal:** the profile as a way to be found, and a state that does not expire on
leaving. **Leave:** the login wall, and the assumption behind it. RC's directory
is visible only to the RC community, so its consent question is low-stakes; ours
is public, indexable and archived, which makes every consent question harder for
us than for RC, not easier. Note also what the manual does *not* say: it promises
alums continued access to the community, not a permanent public profile. Do not
promise that here either.

**[GitHub profile READMEs](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme),
and [Simon Willison's self-updating one](https://simonwillison.net/2020/Jul/10/self-updating-profile-readme/).**
Willison's `README.md` is regenerated by a scheduled GitHub Action: under 150
lines of Python hits the GitHub GraphQL API and his own feeds and replaces
marked comment blocks (`<!-- recent_releases starts -->`). **Steal:** the thesis
of this proposal — a profile assembled from work that already exists never goes
stale, and a hand-written bio always does. **Leave:** the hand-written half, and
the API call; ours reads the content collections it already has. Note what GitHub
itself removed: the *current* and *longest streak* counters, gone since 2016
([dear-github#163](https://github.com/dear-github/dear-github/issues/163), opened
May 2016 and since closed). A streak measures uninterrupted availability, which
during exams measures only that it is exams.

**[CRediT, ANSI/NISO Z39.104-2022](https://credit.niso.org/).** Fourteen named
contributor roles — Conceptualization, Software, Validation, Writing – original
draft — replacing an author list that says only *who was there*. **Steal:** a
small closed vocabulary turns "helped with the bot" into a checkable claim, and
makes non-code work visible without inventing a metric for it. **Leave:**
thirteen of the fourteen names. Ours needs about six, in student language.

**[all-contributors](https://allcontributors.org/en/reference/specification/).**
*"Recognize all contributors - including those that don't push code."* A bot
maintains the table; the
[emoji key](https://allcontributors.org/en/reference/emoji-key/) defines 34
contribution types, among them `doc`, `design`, `translation`, `review` and
`eventOrganizing`. **Steal:** organising, teaching and translating are
contributions of the same kind as code. **Leave:** the emoji key, banned by
`docs/DESIGN.md` §10.4; the contributor-count badge, a number pretending to be a
fact; and thirty of the thirty-four types — a vocabulary that large is one nobody
applies consistently, which is how a closed vocabulary becomes free text.

**[ORCID](https://info.orcid.org/orcid-trust/).** *"All items attached to an
ORCID iD contain a 'source' and date field that shows the provenance of that
information,"* and the holder has *"fine-grained control over the visibility of
information in your ORCID record."* **Steal:** provenance on every entry — a
field that distinguishes what you said about yourself from what someone else
asserted about you — and visibility as the person's decision rather than the
institution's. **Leave:** the registry infrastructure; we need an enum and a
slug, not a resolver.

**[Cambridge — data protection guidance for student clubs and
societies](https://www.information-compliance.admin.cam.ac.uk/data-protection/guidance/societies).**
*"Each University student club and society is responsible for its own
compliance… insofar as the personal data it holds and uses is outside the
control and responsibility of the University."* Societies must issue a privacy
notice to members at the point they join, must *"not keep it for longer than you
need"*, and must handle requests to have information deleted. **Steal:** the
society is the controller — QAIRU will not do this for us — and the notice
arrives at joining, not in a footer. **Leave:** the UK GDPR framing; the
applicable law here is Law No. 94-V.

## Proposal

**1. Link the names that already exist.** Three files render a person as text
where they could render a link. Make them links. No schema change, nothing new
published about anyone, and the site stops discarding a graph it validates.

**2. Consent as a schema object, not a norm.** `consent.listed` is
`z.literal(true)`, so the schema cannot express a person who has not agreed.
Separate booleans govern the page, the photograph and the handles, and
`recordedBy` / `recordedOn` name a human who can be asked what was agreed.

**3. A published removal route.** `src/content/docs/member-record.md`, a
`category: 'process'` document rendering through the existing `/docs/[slug]`
route — no new template — stating what appears, who decides, how to leave, and
what we cannot undo. Cambridge's privacy notice, arriving at joining.

**4. `/people/<slug>`, assembled at build time.** A new
`src/lib/contributions.ts` builds the reverse index once per build: walk
`projects`, `events`, `learn` and `programs`, and for each published entry
referencing a person emit `{ kind, title, date, href, source: 'graph' }`,
reverse-chronologically. Nobody maintains it. Adding a teammate to a project's
`team` array is already how the site learns who built it; now it is also how
their page learns.

**Not `posts`.** `posts.author` is a `reference('people')`, but
`src/pages/blog/` is an empty directory — a post has no URL, so a "wrote" row
would link to a 404. Add `posts` to the walk on the day `/blog` exists, and not
before. `partners` and `docs` carry no person reference at all.

**5. One authored field, capped hard.** `bio`, ≤200 characters, optional — one
sentence about what you are working on, not a CV summary. A page with no `bio`
renders correctly and looks deliberate.

**6. Last, a `contributions` array for what the graph cannot see.** Running the
Telegram bot, translating a note into Kazakh, setting up the room every Friday.
Closed vocabulary, dated, optionally linked. This is the hand-maintained half
and therefore the half that rots, so it ships last or not at all.

Not proposed: a self-service editor, logins, GitHub API calls at build time,
per-member analytics, per-person CODEOWNERS (see Risks — it does not work), or
any new vendor.

## Scope

**Phase 1 (XS — about an hour, ships alone, no schema change).** In
`projects/[slug].astro`, `events/[slug].astro` and `learn/[slug].astro`, render
each resolved person as a link to `/people#<id>` instead of joining names into a
string; and suppress `PeopleStrip`'s link when the strip is already on `/people`,
where it currently links the page to itself. This is worth doing whether or not
the rest of this proposal is ever accepted, and it is the honest floor: the
smallest change that fixes the stated problem without publishing one new fact
about a student.

**Phase 2 (S).** The `consent` object, the `superRefine`,
`scripts/check-consent.mjs` wired into `pnpm check`, and `member-record.md`.
This makes the existing roster honest whether or not any page is ever built, and
**must land before phase 3** — a member page is new publication about a person
and needs a recorded agreement first.

**Phase 3 (S).** `src/lib/contributions.ts`, `/people/[slug].astro`, `bio`, and
the strip linking to the new pages where they exist.

**Phase 4.** The manual `contributions` array; the print stylesheet; the annual
consent-review issue.

## Data and schema

Phase 1 changes nothing here.

**Phase 2** — `src/content.config.ts`, `people` collection:

```ts
consent: z.object({
  listed:  z.literal(true),          // no unconsented entry can validate
  page:    z.boolean().default(false),
  photo:   z.boolean().default(false),
  handles: z.boolean().default(false),
  recordedBy: z.string().min(2),     // a person to ask, not a checkbox
  recordedOn: z.coerce.date(),
  reviewOn:   z.coerce.date(),       // our rule: recordedOn + 12 months
}),
```

`superRefine`: `photo: false` forbids `avatar`; `handles: false` forbids
`github` / `telegram` / `linkedin` / `site`.

`recordedBy` is a free string, not a `reference('people')`, because the person
who had the conversation may not themselves be listed — and requiring them to be
would make recording a consent depend on publishing someone.

**This breaks the build on day one, deliberately.** `z.literal(true)` makes
`consent` required and unfalsifiable, so every existing `people` entry fails
validation until edited. There is exactly one — `example-member.md` — so the
migration cost is one file. But that file is the template `docs/CONTENT.md` tells
a first-time contributor to copy, and it now carries seven more required
sub-fields. See Risks.

**Do not add a `left` field.** Proposal 003 already specifies `until` and
`succeededBy` on this collection for exactly this state, with the rule that
`active: false` requires `until`. Use those names. If 003 is rejected, this
proposal adopts `until` unchanged; the same fact does not need two spellings in
one schema.

`src/lib/content.ts` gains `hasCurrentConsent(person, now)` — `consent.reviewOn
> now`. Expiry never fails the build; a time bomb that breaks an unrelated pull
request is a bug. It downgrades: the page stops being generated, photograph and
handles stop rendering, and the name stays only while `active: true`, because who
currently runs the club is a fact about the organisation rather than a fact about
a private individual. Inactive plus lapsed archives the entry entirely.
`scripts/check-consent.mjs`, run by `pnpm check`, prints anyone within 60 days of
`reviewOn`; phase 4 has a scheduled Action open one issue a year listing them.

**Phase 3** adds `bio: z.string().max(200).optional()`. **Phase 4** adds:

```ts
contributions: z.array(z.object({
  what: z.string().min(8).max(120),
  kind: z.enum(['built', 'hosted', 'wrote', 'organised', 'taught', 'translated']),
  date: z.coerce.date(),
  href: z.url().optional(),
  source: z.enum(['self', 'vouched']).default('self'),  // ORCID's provenance field
  vouchedBy: reference('people').optional(),
})).default([]),
```

with `source: 'vouched'` requiring `vouchedBy`.

`getStaticPaths` for `/people/[slug]` filters to `isPublished(person) &&
consent.page && hasCurrentConsent(person) && rows.length > 0`, where `rows` is
the **merged** list — graph-derived plus any manual entries. Gating on the manual
array alone would deny a page to exactly the people the graph already documents.
Nobody with nothing recorded gets a page; an empty page is worse than no page.

**No D1 migration, no new binding, no runtime cost.** This is content. It must
keep working with the database down.

## Design

DETAIL archetype (§12.2). Cols 2–9: name at `d3`, one mono meta line — `role ·
unit`, plus `ALUMNI` and a leaving date only if 003's `active` / `until` land —
the `bio` sentence, then the contribution list as RECORD (§7.1): hairline rows,
tabular dates, a mono `kind` token, title, and `↗` where a link exists. Cols
11–13: a sticky mono spec table of handles and links, rendered only under
`consent.handles`. Under three rows the list renders as READ per the thin-content
law (§7.4) — which is every new member's page, and should read as *early*, not
broken.

**The PLATE (§7.2) is not a portrait.** Every page carries exactly one; on a
member page it is a photograph of something they built or a session they ran,
captioned and credited — not a large photograph of a student's face. The
"awaiting photography" frame is the default. This keeps the mandatory register
without turning `/people` into a face gallery.

**Cobalt: none of it.** Zero `.cta-primary` — one per page is a ceiling, not a
quota, and an `Apply →` button on someone's personal record would use a student
as a recruitment surface. Nor a cobalt state token: §8.2 gives `--cobalt-text`
only to a state that is *actionable now*, and `ACTIVE` is a fact about a person,
not a door. `ALUMNI` and `ACTIVE` are both `--ink-3`. The only cobalt on the page
is the §8.2 change-bar in the rail, plus focus rings, which are law everywhere.

**A member page prints — but there is no stylesheet to extend.** §12.4 requires
a print stylesheet for the charter; `grep -rn "@media print" src/` returns
nothing, so it has never been written. Phase 4 either writes one for `/docs/*`
and `/people/*` together — light polarity, black rules, one sheet of A4, so the
internship artefact survives being attached to an email — or drops the claim.
Do not describe it as an extension of something that does not exist.

**What must never appear, in any phase.** No activity streak, no contribution
calendar, no "active in the last 30 days". No leaderboard, no ranking, no sort
by volume, and no contribution *count* anywhere — a count is a ranking with the
sorting left to the reader. `/people` keeps the sort `getPeople()` already
uses — explicit `order`, then name — and never gains one by volume. No GitHub
stars, followers or commit counts, or any externally fetched number: a vendor
dependency, unverifiable at build time, and already forbidden by
`docs/CONTENT.md`. No completeness meter, no badges. No email, phone, course,
year of study, home city or student ID — none of it shows what someone built.

## Risks and trade-offs

**The strongest argument for not doing this at all.** There are no members.
`src/content/people/` holds one file, `example-member.md`, marked
`placeholder: true`. Phases 2–4 build a personal-data surface, a consent
vocabulary and a governance document for a roster of zero — the exact failure the
honesty rule exists to prevent, and `docs/STATUS.md` ranks "two or three real
people" as the highest-value missing thing on the whole site. Worse, phase 2
actively obstructs that: proposal 018 exists because the join PR is already too
hard for a first-year, and the `consent` object adds seven required sub-fields to
the very file 018 is trying to make survivable. Meanwhile proposal 003 already
carries the honest half of the consent story (`membership.md`, `until`,
`succeededBy`) at XS. A reasonable decision is: **ship phase 1, reject or defer
phases 2–4, and write real member entries instead.** Phase 1 costs an hour, needs
no consent decision, and leaves nothing to unwind.

**Per-person CODEOWNERS was proposed here and does not work.** The earlier draft
proposed a line per member — `/src/content/people/aisha.md @aisha-gh` — so that a
PR editing what the site says about someone could not merge without their review.
Three problems, each fatal
([GitHub, *About code owners*](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)):
*"The people you choose as code owners must have write permissions for the
repository,"* so every listed student would need write access to the whole repo —
a far larger grant than this proposal is entitled to make; *"the last matching
pattern takes the most precedence,"* so a per-file line placed after
`/src/content/ @tairqaldy` **removes** core review rather than adding to it; and
code owners are only *"automatically requested for review"* — nothing blocks a
merge without a branch-protection rule requiring code-owner approval, which a
sole owner cannot be blocked by anyway (003 makes the same point). What is left
is the ordinary rule, stated as the promise it is: the person's own PR is what
put them on the site, git records who opened it, and a PR editing someone else's
entry without their comment on it does not get merged. That is a norm, not a
mechanism. `member-record.md` should say which it is.

**A page per person publishes a hierarchy.** A third-year with nine rows beside
a first-year with one is a comparison whether or not we call it a leaderboard.
Partly mitigated — no counts, no volume sort, dated entries so a short page reads
as *joined in March* — but not solved. The honest defence is that having a page
is opt-in, and the alternative hides the same hierarchy while also being useless.

**A YAML field is not consent.** `recordedBy` and `recordedOn` record that a
conversation happened; they are not the conversation, and a boolean a lead types
on someone's behalf is exactly the thing the law's "written consent" language is
about. The check guarantees only that someone can be asked who asked.

**Git history is permanent.** Deleting the Markdown removes the page from the
next build; the commit that added it stays in a public repository, in forks and
in the Internet Archive. `member-record.md` must say so in plain words *before*
anyone consents. For a genuine erasure request the escalation is `git
filter-repo` plus a force-push — it rewrites history and breaks every fork, and
that cost is stated rather than promised away. Fifteen business days is the
window the law allows; a force-push is not a fifteen-minute job.

**It turns into a CV site.** If members write for recruiters the record stops
being true. The 200-character cap, the closed `kind` vocabulary and the voice
rules in `docs/CONTENT.md` are the defence: *"Built the Telegram bot that answers
timetable questions"*, never *"spearheaded an AI initiative"*.

**The graph may be thinner than it looks.** The reverse index is only as good as
`team`, `hosts` and `authors` being filled in, and those arrays all default to
`[]`. If contributors omit them — likely, since nothing today rewards filling
them — phase 3 ships empty pages and `getStaticPaths` renders none at all. Phase
1 is the cheap test: once names are links, an empty `Team` row is visibly a
missing fact rather than an absent field.

## Success

Phase 1 succeeds if `pnpm check` and `pnpm e2e` pass and no person's name renders
as dead text on any detail page. That is checkable today.

Phases 2–4 are measured a term after there are real members to measure — not a
term after the code merges. Then: every published `people` entry carries a
`consent` block naming who asked and when; the majority of member pages carry
three or more dated rows, none typed by hand; no `reviewOn` has lapsed unnoticed;
and one removal request, real or rehearsed, completes end to end within the
fifteen business days the law allows.

Rewrite or remove this if more than a third of `contributions` rows are
`vouched` rather than `self` (people are not recording their own work); if the
median page still has one row after two terms (the graph was never real and the
pages are decoration); if the `consent` block is measurably slowing down people
joining, which 018 will notice before this proposal does; if anyone asks for a
count, a streak or a ranking and we agree; or if a member asks to be removed and
finds it harder than `member-record.md` promised. That last one alone is enough
to take the feature down.

## Effort

**Phase 1: XS — about an hour.** Three detail templates, one strip prop, one
Playwright assertion. No schema change, no new content, no decision about anyone
who does not exist yet. Ships alone.

**Phase 2: S — about a day.** Consent object, `superRefine` and
`check-consent.mjs` wired into `pnpm check`: 4h. `member-record.md`, plus the
consent wording someone actually reads aloud: 4h.

**Phase 3: S — about a day.** `contributions.ts` and its unit tests: 3h.
`/people/[slug].astro`: 4h. Copy, screenshots at 375 / 768 / 1440 in both themes,
§16 pass: 2h.

**Phase 4: M.** The manual array: 2h. The print stylesheet §12.4 has always
required and nobody has written, for `/docs/*` and `/people/*`: 4h. The annual
review Action: 1h.

Overlaps 003, which owns `until` / `succeededBy` and the meaning of `active`, and
018, which owns how hard the join PR is allowed to be. Phase 3 is blocked on
there being real members and real projects — the content unblock `docs/STATUS.md`
already asks for, and the thing worth doing instead of this.
